# Agent Task Contract

一个探索「AI Agent 之间如何基于证据协作」的实验性协议。

> **最少的规则 · 足够强的验证**
> 让 Agent 自己决定如何工作，让证据决定工作是否完成。

这个仓库记录了一次具体实验：两个能力不同的 Agent —— **Hermes**（桌面端 Agent，充当协调方）与
**dsh / DeepSeek Harness**（沙箱内 Agent，充当执行方）——先做同题对比，后来在一份书面契约下开始协作。
契约目前迭代到 **v2.3**。它记录的是「试过什么」，不是一个已被证明的方法。

- 协议正文：[`SPEC.md`](SPEC.md)（权威文本，中文）
- 任务模板：[`TASK.template.md`](TASK.template.md)
- 报告 Schema：[`REPORT.schema.json`](REPORT.schema.json)
- 真实运行记录：[`examples/`](examples/)
- 历史版本：[`history/`](history/)

## 一、为什么先做对比

项目起点是一个很实际的问题：**手上有多个 Agent 时，某项任务该交给谁？**

最初的设想是打一场对照赛：两边拿到同样三份任务书，由 Hermes 用同一套标准验收，再根据结果决定
"哪类活给谁"。

三份任务覆盖不同能力：

| 编号 | 任务 | 考察点 |
| --- | --- | --- |
| P1 | 单文件排序可视化（`index.html` + `selftest.js`） | 前端代码、动画、可测试结构 |
| P2 | 零依赖 CSV 统计 CLI（`csvstat.js` + `test.js`） | 解析、命令行语义、退出码 |
| P3 | Node.js 单文件打包技术简报 | 检索、引用、事实准确度 |

2026-10-20，两个 Agent 各做了一遍，对比记录在
[`examples/00-comparison-report.md`](examples/00-comparison-report.md)。

**对比实际说明了什么**（n = 1，没有重复测量，没有对照组）：

- dsh 的自证更深：P1 做了 7 组输入、354 条断言，自己写了无头浏览器脚本截图；P3 的 19 条一手来源
  全部通过 URL 抽查。
- Hermes 交付更快、节奏更稳；dsh 的 35 分钟里有约 26 分钟在等两个永不返回的工具调用。
- 两边都不能被推广。每个任务只跑一次，无法区分能力和运气。

## 二、为什么转向协作

对比的前提是"要选出一个赢家"。但实际做下来，更有用的问题是：**能不能按强项分工，让一方验收另一方？**

这需要对比阶段没有的东西：契约。一旦发生交接，立刻出现三个问题：

1. 执行方看不到协调方的意图。任务书少写一项，她只能自己猜。
2. "做完了"对两边含义不同。没有机器可判定的标准，执行方会按自己的完成感收工。
3. 执行方的自述不是证据。有两次运行她返回 `status: done` 但总结为空，最终只能以磁盘文件为准。

## 三、协议想解决什么

这份契约的野心很小：让交接**可核对**，让验收**不依赖执行方的自述**。

覆盖的范围：

| 方面 | 回答的问题 |
| --- | --- |
| 任务定义 | 任务书必须包含什么，才能开工 |
| 预算与超时 | 一个任务最多做多久，到点怎么办 |
| 停止条件 | 什么算"够好"，要写成脚本能判定的形式 |
| 证据 | 必须留下什么文件，什么格式 |
| 独立验收 | 协调方如何在不信任报告的情况下复核 |
| 隔离 | 执行方能写哪里，用哪个会话 |
| 失败处理 | 取消、超时、工具卡死时怎么办 |
| 重新分配 | 什么时候续接，什么时候重派 |

## 四、协议是怎么长出来的

没有任何一条是提前设计的。每一版都来自上一版暴露的问题。

| 版本 | 触发 | 改动 |
| --- | --- | --- |
| v1.0 | 第一次交接 | 五项基础：产物路径、验收命令、预算、禁止项、允许工具 |
| v1.1 | 协调方复核 | 加交付物清单、自检可修一次、超时按命令分级、目录隔离、证据格式 |
| v1.2 | 执行方补丁 | 可核验字段、long-run 默认配额、改测试审计、版本单源 |
| v1.3 | 协调方补丁 | lite 模式、自检超限后果、续接判据改为时间差值 |
| v1.4 | 执行方补丁 | 自检按类计数、超时闸门、`stop-and-report` 合法出口 |
| v2.0 | 合并 | 以上收口；加看门狗与 stop-and-report 触发条件 |
| v2.1 | 首次 lite 运行 | 实测回填：`timeoutMs` **不 kill**、会话无法通过 API 新建、证据日志必须 UTF-8 |
| v2.2 | 第二次运行 | 命令级超时脚本与调用约定、看门狗按预算缩放、字段定死 12、串味抽查 |
| v2.3 | 协调方 | 预算三档；复杂任务必须拆阶段；"没做完"≠"做砸了" |

完整 diff 在 [`history/`](history/)。

## 五、两次真实运行确认了什么

只有两次 lite 运行，而且都是拿协议本身做对象。这是本仓库全部的经验证据。

**运行 1 —— 契约检查器（`examples/04-contract-check-lite-run/`）**

写了一个零依赖的 Markdown 检查器，检查章节编号、`§` 引用、JSON 块、`report.json` 字段数。
独立复跑通过（exit 0）；喂一份故意写坏的文件，它报出 5 条带行号的准确错误（exit 1）。
这次运行还得到两个负面结论：

- `task_result` 返回的 `assistantText` 和 `stats` 都是空的，验收只能看文件。
- 证据日志被 PowerShell 重定向写成 UTF-16LE，按文本读是乱码，直到契约强制 UTF-8 才修好。

**运行 2 —— 超时守卫（`examples/05-timeout-guard-run/`）**

探针证明 harness 的 `timeoutMs` **不会终止**命令：60 秒的命令设 25 秒超时，实际跑满
（`killed: false`）。执行方随后写了包装脚本，到点杀进程树。实测：30 秒命令设 5 秒超时，
5.16 秒被杀、孙进程确认死亡；3 秒命令设 10 秒超时，3.53 秒正常退出。协调方独立复跑，
复现 5.152 秒。

这两次运行说明的是**具体机制有效**，不是"协议整体提升了效果"——没有和基线比较。

## 六、v2.3 是什么，不是什么

**是**：一份能用的、明显偏臃肿的契约。它扛过两次真实交接和一轮调试，规则具体到 Agent 能执行、脚本能检查。

**不是**：经过验证的方法、框架或产品。具体地：

- 没有对照组。没有任何"不用契约"的测量。
- n = 1。所有任务、所有运行都只发生一次。
- 单一环境：一台 Windows 机器、每个 Agent 一个模型、一个 harness 版本。
- 与实现绑定。多条规则默认了这套搭配的工具：PowerShell 沙箱、MCP 桥、`sessionId` 语义。
  `SPEC.md` 把它们标成 implementation note，但照抄到别的环境不能直接用。
- 未验证的规则。看门狗从未在真实卡死中触发，参数仍标着"待校准"。

## 七、为什么继续加规则可能是错的

契约从 329 tokens 长到约 1,200。这个增长有代价：

- 每次派发要填六七项，每次验收要核十二个字段。
- 小任务花在契约上的上下文比干活还多。
- 从未被触发的规则（看门狗）看起来像保证，其实是未测代码。
- 好几条规则来自一次孤立事件，单个事件不足以支撑一条永久规则。

所以下一阶段是**做减法**，不是继续加：找出真正改变结果的规则，删掉其余的。

## 八、下一步是实验，不是结论

计划在同一组任务上比较三种配置：

| 配置 | 说明 |
| --- | --- |
| 无协议 | 只给任务，不给任何协作规则 |
| 极简协议 | 只保留任务定义与结果验证 |
| v2.3 | 当前完整契约 |

每个任务测量：成功率、错误率、返工次数、完成时间、Token 消耗、人工介入次数、重派次数、
验收阶段发现的问题。

目的不是证明 v2.3 正确，而是找出**哪些规则值得保留**。收益有限、复杂度明显的规则应当被删除。

以上都还没跑，是计划。
